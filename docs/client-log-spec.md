# Chronos 로그 수집 - 서버 연동 명세

**대상:** Unity 클라이언트 담당
**개정:** 2026-08-03 (v2 — 클라 로그 파이프라인 실태 반영)
**전시:** 8/15 부산

---

## 0. 요약 (바쁘면 이것만)

**클라 로그 시스템은 이미 완성돼 있습니다. 새로 만들 것 없습니다.**
서버가 기존 `ClientLogEnvelope` 포맷에 맞춰 받도록 구현했습니다.

**필요한 작업은 사실상 하나입니다:**

```
LogManager의 ServerUrl 을 아래로 설정
→  http://localhost:8080/api/v1/logs
```

이것만 하면 로그가 DB에 적재됩니다.
나머지(1장 요청사항)는 데이터 품질을 높이는 항목이며, 시간이 없으면 생략 가능합니다.

---

## 1. 클라 요청사항 (우선순위순)

### 🔴 필수

**① `ServerUrl` 설정**
```
http://localhost:8080/api/v1/logs
```
전시 부스에서 게임과 서버가 같은 PC에서 돌 예정이므로 `localhost`입니다.
(부스 PC가 여러 대가 되면 서버 PC의 IP로 변경 — 8/10 리허설 때 확정)

### 🟠 강력 권장 — 데이터 신뢰도가 걸린 항목

**② 전시 빌드에서 "이어하기(Continue)" 비활성화**

전시장에서는 관람객이 **게임을 끝내지 않고 그냥 자리를 뜨는 경우**가 대부분입니다.
이때 `RUN_END` 없이 세션이 디스크에 남고, **다음 관람객이 Continue를 누르면
서로 다른 두 사람의 플레이가 같은 `runId`로 기록됩니다.**

`runId`는 서버에서 **플레이어 수를 세는 유일한 기준**이므로, 이 경우 집계가 무의미해집니다.

- 요청: 전시 빌드에서 메인메뉴의 **Continue 버튼을 숨기거나 비활성화**
- 관람객은 이어하기를 사용할 일이 없으므로 UX 손해도 없습니다
- 작업량: 버튼 하나 비활성화

> 이 항목은 아래 ③④보다 우선순위가 높습니다.
> 데이터의 양이 아니라 **신뢰도 자체**가 걸린 문제입니다.

### 🟡 권장 (데이터 품질)

**③ 오버클럭(타이머) 잔량을 로그에 포함**

HP가 사라지고 타이머가 그 역할을 하게 되면서, **잔여 시간이 가장 중요한 지표**가 되었습니다.
현재 어떤 이벤트에도 실리지 않고 있습니다.

- 접근자: `StageRuntimeManager.Instance.CurrentOverclockSeconds` (float, 초)
- 요청: **엔벨로프 공통 필드로 추가**하거나, 최소한 `PLAYER_DEATH` / `RUN_END` / `FLOOR_CLEAR` payload에 포함
- 필드명 제안: `overclockRemainingSec` (초 단위)

> 이 값이 있으면 "몇 초 남았을 때 죽는가", "어느 구간이 시간을 많이 소모하는가"를
> 분석할 수 있습니다. 없으면 타이머 관련 분석이 전부 불가능합니다.

**④ 런 처치 수를 `RUN_END` / `PLAYER_DEATH` payload에 추가**

- 접근자: `StageRuntimeManager.Instance.CurrentRunKillCount` (int)
- 필드명 제안: `killCount`

**⑤ `PLAYER_DEATH` / `RUN_END` 의 실제 플레이 시간 확인**

`survivalTimeMs` / `totalTimeMs` 가 `runElapsedSeconds` 기준으로 채워지는지 확인 부탁드립니다.
세이브의 `totalPlayTimeMs`는 증가시키는 코드가 없어 항상 0인 것으로 파악됩니다.
**플레이 시간은 전시 발표의 핵심 지표라 이 값이 0이면 곤란합니다.**

### ⚪ 여유 되면

**⑥ `FLOOR_ENTER` / `RUN_RESUME` 의 `round`를 논리 라운드로 통일**

현재 이벤트별로 물리/논리 라운드가 섞여 들어옵니다 (3장 참고).
서버는 양쪽 다 받도록 만들어두었으므로 **급하지 않습니다.**

**⑦ `clientVersion`을 엔벨로프 공통 필드로**

현재 `ACCOUNT_LOGIN` payload에만 있습니다.
전시 중 빌드를 교체할 경우 "어느 빌드에서 나온 로그인지" 구분이 필요합니다.

## 2. 서버가 받는 포맷 (현행 유지 — 변경 없음)

`ClientLogEnvelope`가 지금 보내는 형태 그대로 받습니다.

```json
[
  {
    "userId": -6601403713907716966,
    "eventType": "RUN_START",
    "timestamp": "2026-08-15T13:24:05.123Z",
    "difficulty": "LIMITED",
    "runId": -8553994346255530530,
    "floor": 1,
    "round": 1,
    "payload": { "characterClass": "WARRIOR" }
  }
]
```

| 필드 | 타입 | 서버 처리 |
|---|---|---|
| `userId` | number | 그대로 저장. **기기 식별용** (4장 참고) |
| `eventType` | string | 그대로 저장. 모르는 값이 와도 저장됨 |
| `timestamp` | string (ISO-8601) | `client_time`으로 저장. 없으면 서버 수신 시각으로 대체 |
| `difficulty` | string | 그대로 저장 |
| `runId` | number | 그대로 저장. **가장 중요한 값** |
| `floor` | number | 그대로 저장 |
| `round` | number 또는 string | **둘 다 받습니다.** 문자열로 저장 |
| `payload` | object | JSONB로 저장. **자유 형식** |

**키가 생략되는 필드가 있어도 문제없습니다.**
`ACCOUNT_LOGIN`처럼 `runId` / `floor` / `round`가 없는 이벤트는 해당 컬럼이 NULL로 저장됩니다.
서버 테이블에서 `NOT NULL`인 컬럼은 `event_type`과 서버 수신 시각 두 개뿐입니다.

**서버가 자동으로 채우는 값 (클라 전송 불필요):**
- `server_time` — 수신 시각
- `env` — 서버 실행 프로필 기준 (`expo` / `local`)

### payload는 자유롭게 확장 가능합니다

payload는 JSONB로 저장되므로 **필드를 추가해도 서버 수정이 필요 없습니다.**
새 이벤트 타입을 추가해도 마찬가지입니다. 서버에 알리지 않아도 그대로 적재됩니다.

다만 아래만 지켜주시면 분석이 쉬워집니다:
- 같은 의미는 항상 같은 키 이름 (`killCount`와 `kills`를 섞지 않기)
- 시간 단위를 키 이름에 명시 (`~Sec`, `~Ms`)
- 숫자는 숫자로

## 3. 알려진 데이터 특성 (서버/분석 측 인지 사항)

클라 수정 요청이 아니라, **분석할 때 주의할 사항**을 기록해둡니다.

### ① `round` 필드에 두 체계가 섞임

| 이벤트 | 값의 종류 |
|---|---|
| `FLOOR_ENTER`, `RUN_RESUME` | **물리** 라운드 (시드로 셔플된 씬 번호) |
| `PLAYER_DEATH`, `RUN_END`, `FLOOR_CLEAR`, `BOSS_KILL` | **논리** 라운드 (진행 순번, 보스 = 필드 수 + 1) |

**진행도 분석(어디까지 갔나, 어디서 죽나)은 논리 라운드를 쓰는 이벤트에서만 뽑을 것.**
`FLOOR_ENTER`의 round로 진행도를 계산하면 틀립니다.

### ② 현재 항상 고정값인 필드 — 분석에 쓰지 말 것

| 필드 | 이벤트 | 상태 |
|---|---|---|
| `killerId` | `PLAYER_DEATH` | 항상 null (추적 코드 없음) |
| `deathsInFloor` | `FLOOR_CLEAR` | 항상 0 |
| `characterClass` | `RUN_START` | `"WARRIOR"` 하드코딩 |
| `region` | `ACCOUNT_LOGIN` | `"KR"` 하드코딩 |
| `bossId` | `BOSS_KILL` | `F{floor}_B` 형식으로 생성됨 (실제 보스 ID 아님) |

### ③ `CLIENT_ERROR` 이벤트는 호출부가 없어 발생하지 않음

### ④ 시간 단위가 혼재

- 로그 payload: **밀리초** (`~Ms`)
- 오버클럭: **데시초** (1/10초, `overclockDeciseconds`) — 초 변환 시 `/10`
- 런타임 접근자: **초** (float)

## 4. `userId`는 "사람"이 아닙니다

`userId`는 **설치(기기) 단위 식별자**입니다. 최초 세이브 생성 시 1회 발급되고 계속 유지됩니다.

전시장에서는 관람객 수백 명이 **모두 같은 `userId`**를 갖게 됩니다.

- ❌ `userId`로 플레이어 수를 세면 안 됨
- ✅ **부스 PC 구분용**으로는 유용 (여러 대일 경우)
- ✅ 플레이어 수 = **`COUNT(DISTINCT run_id)`**

`runId`(= `SeedManager.MasterSeed`)는 `StartNewRun`에서 판마다 1회 발급되고 런 중 불변이므로,
**판(플레이 1회) 단위 식별자로 정확히 동작합니다.**

---

## 5. ⚠️ 테스트 시 주의 — 전송 차단 게이트 3종

아래 중 **하나라도 걸리면 로그가 큐에 들어가지도 않습니다.**

| 게이트 | 조건 | 테스트 시 대응 |
|---|---|---|
| `ServerUrl == ""` | URL 미설정 | 1장 ① 참고 |
| `Application.isEditor` | **유니티 에디터 플레이** | **반드시 빌드해서 실행할 것** |
| `SeedManager.MasterSeed == 0` | 개발용 직접 플레이 | 로비에서 정상적으로 런 시작할 것 |

**연동 테스트할 때 에디터에서 플레이하면 로그가 하나도 안 옵니다.** 빌드 필수.

## 6. 전송 동작 (참고)

| 항목 | 값 |
|---|---|
| 배치 주기 | 15초 |
| 배치 크기 | 20건 |
| 재시도 | 지수 백오프 2s → 60s |
| 큐 상한 | 500건 (초과 시 오래된 것부터 폐기) |
| 종료 시 | `pending_logs.ndjson`으로 영속화 |

> 서버가 꺼져 있어도 게임은 정상 동작하며, 로그는 큐에 쌓였다가 재전송됩니다.
> 다만 **서버가 오래 죽어 있으면 500건 상한에 걸려 오래된 로그부터 유실**되므로,
> 전시 중에는 서버 상태를 주기적으로 확인합니다.

## 7. 확인 필요 사항 (회신 요청)

- [ ] ⚠️ **게임에 시드 직접 입력 기능이 있는지** — 있으면 서로 다른 플레이어의 `runId`가 겹칠 수 있음
- [ ] `survivalTimeMs` / `totalTimeMs` 가 실제로 채워지는지 (1장 ④)
- [ ] 전시 부스 **게임 PC 대수** — 1대 / 여러 대?
- [ ] 전시 PC에 **서버·DB 설치**가 가능한지 (관리자 권한 필요)
- [ ] 중도 이탈(관람객이 그냥 자리를 뜸) 시 `RUN_END`가 발생하는지
      → 발생하지 않는다면 이탈 시점 추정을 위해 주기적 `heartbeat` 이벤트 추가를 검토
      (서버는 `RUN_END` 없는 런을 `ABANDONED`로 분류하고, 마지막 이벤트 시각을 종료 시각으로 간주합니다)
