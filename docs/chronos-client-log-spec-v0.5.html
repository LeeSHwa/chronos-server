클라이언트 작업 목록

v0.4 → v0.5에서 클라이언트가 바꿔야 하는 것만 모았습니다. 자세한 내용은 각 장을 보세요.

필수

  1. RUN_START의 characterClass를 attackType으로 교체. 로비에서 고른 공격 타입(기본값 산탄)을 SPECIAL_SHOT / PRECISION_TARGETING / CONVERSION 중 하나로 보냅니다. 2.2
  2. build를 담는 위치를 ROUND_CLEAR · PLAYER_DEATH · RUN_END로 옮김. ROUND_ENTER에서는 뺍니다. 3.2 · 3.3 · 3.4
  3. 킬 수 관련 key(roundKillCount, runKillCount) 전부 삭제. 1.5
  4. PLAYER_DEATH에 deathCause와 killerId 추가. 피격 처리 경로에 가해자를 실어 보내면 됩니다. 3.4
  5. FLOOR_ENTER는 층이 바뀔 때만 발행, 라운드 진입은 ROUND_ENTER로 분리. 1.5
  6. 보스 처치는 보스 스테이지의 ROUND_CLEAR 하나로 기록. BOSS_KILL · FLOOR_CLEAR 삭제. 1.5
  7. ROUND_CLEAR는 Save 시점에 발행하고, 클리어 순간의 시간·OC는 clearElapsedMs · clearOverclockDeciseconds로 따로 담습니다. 3.3
  8. 빌드 스냅샷 기능을 새로 만들어야 합니다. 전투가 끝난 순간(마지막 적 처치 / 보스 HP 0 / 사망)에 현재 장착·보유 상태를 사본으로 떠서 얼려 두고, 로그를 보낼 때 그 사본을 싣습니다. 리워드·정비로는 갱신하지 않습니다. 3.5
  9. round를 모든 이벤트에서 진행 순서로 통일. 보스는 "B". 1.3
  10. 시간 key를 elapsedMs 하나로 통일 (survivalTimeMs · totalTimeMs · clearTimeMs 삭제). 1.8
  11. 1-1 진입 로그를 첫 진입 리워드를 고른 뒤로 이동. 4.2
  12. CLIENT_ERROR 호출부 연결 (지금은 보내는 곳이 없습니다). 2.5

다음 단계 (이번 작업 범위 밖, 합의만 해두는 것)

  1. REWARD_PICK — 제시된 카드 3장과 고른 1장을 남기는 이벤트. 지금은 고른 결과만 알 수 있고 무엇 중에 골랐는지를 몰라서 카드 밸런스를 볼 수 없습니다. 발행 시점은 ROUND_CLEAR 뒤 리워드 선택이 확정되는 순간입니다.
  2. RELIC_WAGER — 보스에서 OC가 0이 됐을 때 열리는 성물 베팅의 결과. 판당 1회뿐이지만 판 성패를 직접 가릅니다.
  3. 가호(blessings) — 고른 목록이 클라이언트에 남지 않고 합산 스탯만 있어, 이번 build에서는 뺐습니다. REWARD_PICK이 들어가면 그쪽에서 내역이 복원됩니다.

로그 구조와 이벤트 타입

모든 로그가 공통으로 갖는 필드와 이벤트 타입 전체 목록입니다.

1.1전송 흐름

Unity 클라이언트LogManager
→ JSON 배열 →
Chronos 서버POST /api/v1/logs
→
PostgreSQLgame_events

로그 한 건은 공통 필드와 payload로 나뉩니다. 공통 필드는 테이블의 일반 컬럼이 되어 필터와 집계에 바로 쓰이고, payload는 이벤트마다 다른 상세 정보로 JSONB 컬럼 하나에 그대로 저장됩니다.

클라이언트는 로그를 큐에 쌓아 15초마다 최대 20건씩 묶어 보냅니다. 전송에 실패하면 순서를 지킨 채 다시 보내고, 게임을 끄면 남은 로그를 디스크에 저장했다가 다음 실행 때 이어서 보냅니다.

// 요청 본문 예시
[
  {
    "userId": -6601403713907716966,
    "eventType": "ROUND_CLEAR",
    "timestamp": "2026-10-05T13:24:05.1234567Z",
    "difficulty": "Standard",
    "runId": -8553994346255530530,
    "floor": 1,
    "round": "2",
    "payload": {
      "clearElapsedMs": 84210,
      "clearOverclockDeciseconds": 731,
      "build": { "weapons": [ ... ], "runes": [ ... ], "augments": [ ... ] }
    }
  }
]

1.2공통 필드

클라이언트의 ClientLogEnvelope가 모든 이벤트에 붙이는 8개 필드입니다. 현행 구성을 그대로 유지합니다.

필드타입DB 컬럼발행 시점설명
userIdlonguser_id모든 로그게임이 설치된 기기마다 하나씩 발급되는 번호입니다. 사람이 아니라 기기를 구분하므로, 재설치하면 새 유저로 잡힙니다.
eventTypestringevent_type모든 로그무슨 일이 일어났는지를 나타내는 이름입니다. 예: RUN_START, PLAYER_DEATH
timestampstringclient_time모든 로그클라이언트에서 로그를 만든 시각(UTC)입니다. 같은 스테이지 안에서 일이 일어난 순서를 볼 때 씁니다.
difficultystringdifficulty모든 로그이번 판의 난이도입니다. Standard, Endless, Limited, Timeless 중 하나이며, 판 밖에서 나간 로그에서는 의미가 없습니다.
runIdlongrun_id런 시작 후한 판을 구분하는 번호입니다. 같은 runId를 가진 로그를 모으면 한 판의 기록이 됩니다. 지금은 런 시작 때 발급되는 시드 값을 그대로 씁니다.
floorintfloor스테이지 진입 후지금 몇 층에 있는지입니다. 1층부터 셉니다.
roundstringround스테이지 진입 후그 층에서 몇 번째 스테이지인지입니다. 필드는 "1"부터 차례로, 보스는 "B"입니다. 맵 순서가 섞여도 플레이어가 지나간 순서대로 매깁니다.
payloadobjectpayload이벤트마다 다름이벤트마다 달라지는 상세 정보입니다.

서버가 채우는 컬럼: id(일련번호), server_time(수신 시각). 해당하지 않는 필드는 key를 생략하며, 서버에는 NULL로 저장됩니다.

1.3스테이지를 가리키는 값

스테이지는 필드와 보스 두 종류입니다. 리워드와 정비는 포탈을 타는 도중에 나오는 화면이라 스테이지로 세지 않습니다. 1층 필드 4개는 판마다 순서가 섞이므로, "몇 번째로 들어간 스테이지인가"와 "어떤 맵인가"를 따로 기록합니다.

값위치예시용도
floor · round공통 필드1 · "1" … 1 · "4", 1 · "B"플레이어가 지나간 순서입니다. 문자열로 정렬해도 "1" < "2" < … < "B" 순서가 됩니다.
mapIdROUND_ENTER payload"F1_3", "F1_B"실제로 들어간 맵의 씬 이름입니다. 몇 번째 자리에서 나왔는지와 상관없이 맵 단위로 묶을 때 씁니다.

클리어나 사망 같은 다른 스테이지 이벤트는 맵을 싣지 않고, 같은 runId·floor·round의 ROUND_ENTER에서 가져옵니다. 이 둘을 나눠 두면 "F1_3이 어려운 것"과 "3번째 자리가 어려운 것"을 분리해서 볼 수 있습니다.

1.6한 시점에 여러 건이 나가는 경우

시점발행 순서
로비 포탈RUN_START → (첫 진입 리워드) → FLOOR_ENTER → ROUND_ENTER
층이 바뀌는 포탈ROUND_CLEAR → FLOOR_ENTER → ROUND_ENTER
같은 층 안의 포탈ROUND_CLEAR → ROUND_ENTER
플레이어 사망PLAYER_DEATH → RUN_END
마지막 보스 처치ROUND_CLEAR → RUN_END

클라이언트는 실패한 로그도 순서를 지켜 다시 보내므로, 서버의 id 순서가 곧 발행 순서입니다.

1.7payload 작성 규칙

  • key는 camelCase로 씁니다.
  • 시간과 OC는 클라이언트가 재는 단위를 그대로 쓰고, key 이름 끝에 단위를 붙입니다. 예: elapsedMs(밀리초), overclockDeciseconds(0.1초)
  • payload 안의 ENUM 값은 UPPER_SNAKE_CASE로 씁니다. 예: DEATH, SPRING
  • 값이 없으면 key를 생략하고 null을 넣지 않습니다.
  • 같은 의미에는 모든 이벤트에서 같은 key를 씁니다.
  • 장비·룬·증강 구성은 어느 이벤트에서든 같은 모양의 build 객체로 담습니다.

1.8시간과 OC 기준

  • 플레이 시간 elapsedMs: 이번 판에서 실제로 플레이한 누적 시간입니다. 이어하기를 해도 이어서 셉니다.
  • OC 잔량 overclockDeciseconds: 게임 안의 제한 시간이자 체력입니다. 0.1초 단위입니다.
  • 스테이지 소요 시간은 ROUND_CLEAR의 clearElapsedMs에서 같은 스테이지 ROUND_ENTER의 elapsedMs를 뺀 값입니다. ROUND_CLEAR는 리워드와 정비가 끝난 뒤에 나가지만 클리어한 순간의 값을 따로 담으므로, 리워드와 정비 시간은 스테이지 소요 시간에 섞이지 않습니다.
  • OC 지급 규칙은 로그에 적지 않습니다. 라운드 지급분이 얼마인지, 언제 들어오는지는 클라이언트의 규칙이고, 로그는 그 결과인 그 순간의 잔량만 적습니다. 규칙이 바뀌어도 로그 형식은 바뀌지 않습니다.
  • 그래서 기준만 분명히 해 둡니다 — ROUND_ENTER의 OC는 그 라운드 지급분이 들어오기 전, ROUND_CLEAR의 OC는 들어온 뒤입니다.

변경
발행 시점

2.3RUN_RESUME

현행
발행 시점
메인 메뉴에서 이어하기를 누를 때

key타입설명

2.4RUN_END

변경
발행 시점
  • 클리어: 마지막 층의 보스를 쓰러뜨린 순간. 보스가 없는 층이 마지막이면 그 층 마지막 필드의 포탈을 탄 순간
  • 사망: PLAYER_DEATH 바로 뒤
  • 포기: 판이 진행 중일 때 로비나 메인 메뉴로 나간 순간 신규
공통 필드
runId, floor, round 있음. 판이 끝난 위치입니다.
key타입설명
resultstring끝난 이유입니다. ENUM: WIN, DEATH, QUIT
elapsedMslong판 전체의 플레이 시간입니다.
overclockDecisecondsint끝난 시점의 OC 잔량입니다. 사망이면 0입니다.
buildobject판이 끝난 시점의 장비·룬·증강입니다. 신규
 
{ "result": "DEATH", "elapsedMs": 412880, "overclockDeciseconds": 0, "build": { ... } }

게임을 그냥 끄면 RUN_END가 나가지 않습니다. 이런 판은 마지막 로그 시점에 멈춘 판으로 봅니다.

스테이지 이벤트와 build

스테이지에 들어가고, 클리어하고, 죽는 순간의 이벤트입니다. 마지막 절에 장비·룬·증강을 담는 build 객체의 구조를 정리했습니다.

3.1FLOOR_ENTER

변경
발행 시점
새 층에 들어갈 때. 판 시작의 1층 진입도 포함하며, 바로 뒤에 같은 스테이지의 ROUND_ENTER가 나갑니다.
공통 필드
runId, floor 있음. round는 그 층에서 처음 들어가는 스테이지의 값입니다.
key타입설명
fieldCountint이 층의 필드 수입니다. 지금 1층은 4, 2층은 1입니다.
hasBossbool이 층에 보스 스테이지가 있는지입니다. 지금 2층은 보스 없이 마지막 필드가 층의 끝입니다.

3.2ROUND_ENTER

신규
발행 시점
포탈을 타고 리워드와 정비를 마친 뒤, 다음 스테이지를 불러오기 직전. 세이브와 같은 시점입니다. 1-1은 첫 진입 리워드를 고른 직후입니다.
공통 필드
runId, floor, round 있음. 들어가는 스테이지 기준입니다.
key타입설명
mapIdstring들어가는 맵의 씬 이름입니다. 예: "F1_3", "F1_B"
elapsedMslong이 시점의 누적 플레이 시간입니다. 스테이지 소요 시간의 시작점입니다.
overclockDecisecondsint이 시점의 OC 잔량입니다. 이번 스테이지에서 받을 라운드 지급분은 아직 들어오기 전입니다.
 
{ "mapId": "F1_3", "elapsedMs": 84210, "overclockDeciseconds": 731 }

build는 싣지 않습니다. 필드에 도착한 뒤 첫 입력 전까지 장착을 바꿀 수 있어서, 이 시점의 구성이 실제로 그 스테이지를 플레이한 구성과 다를 수 있기 때문입니다. 구성은 ROUND_CLEAR에 담습니다. 스테이지별 진입 수를 세는 기준이 되는 이벤트입니다.

3.3ROUND_CLEAR

신규
발행 시점
  • 스테이지를 클리어하고, 포탈을 타서 리워드 선택과 정비를 마쳐 Save되는 순간. 다음 스테이지의 ROUND_ENTER 바로 앞에 나갑니다.
  • 마지막 층의 보스는 다음 스테이지가 없으므로 쓰러뜨린 순간에 나가고, 바로 뒤에 RUN_END(WIN)가 이어집니다.
공통 필드
runId, floor, round 있음. 클리어한 스테이지 기준입니다.
key타입설명
clearElapsedMslong클리어한 순간의 누적 플레이 시간입니다. 필드는 예정된 적을 모두 처치한 순간(예정된 적이 없으면 포탈을 탄 순간), 보스는 HP가 0이 된 순간입니다. ROUND_ENTER의 elapsedMs와의 차이가 그 스테이지의 소요 시간입니다.
clearOverclockDecisecondsint클리어한 순간의 OC 잔량입니다. 그 라운드 지급분은 이미 들어온 뒤입니다.
buildobject클리어한 순간의 장비·룬·증강입니다. 로그는 Save 시점에 나가지만 이 값은 그 전에 찍어 둔 스냅샷이며, 리워드 선택과 정비는 반영되지 않습니다. 신규
 
{ "clearElapsedMs": 84210, "clearOverclockDeciseconds": 731, "build": { ... } }

이 이벤트에 실리는 세 값은 모두 클리어한 순간에 찍어 둔 것입니다. 로그가 나가는 시점(Save)과 값이 가리키는 시점(클리어)이 다른 유일한 이벤트입니다. 스냅샷 규칙은 3.5를 보세요. 보스 스테이지의 ROUND_CLEAR가 지금의 BOSS_KILL과 FLOOR_CLEAR를 대신합니다.

3.4PLAYER_DEATH

변경
발행 시점
OC가 0이 되어 플레이어가 죽은 순간. 바로 뒤에 RUN_END(DEATH)가 나갑니다.
공통 필드
runId, floor, round 있음. 죽은 스테이지입니다.
key타입설명
deathCausestringOC를 마지막으로 깎은 원인입니다. ENUM: DRAIN(시간이 흘러 바닥남), COMBAT(적에게 맞음), REFLECT(보스 돌진 반사 — Timeless 전용) 신규
elapsedMslong죽은 순간의 누적 플레이 시간입니다.
killerIdint마지막으로 피해를 준 적의 id입니다. 시간 소진처럼 가해자가 없으면 key를 생략합니다. 신규
buildobject사망 시점의 장비·룬·증강입니다. 신규
 
{ "deathCause": "COMBAT", "elapsedMs": 468000, "killerId": 2010, "build": { ... } }

죽은 판은 ROUND_CLEAR가 나가지 않으므로, 여기에 build가 없으면 그 판의 구성을 알 수 없습니다. killerId는 피해를 주는 쪽에서 자기 id를 함께 넘기면 됩니다 — 모든 피격이 같은 차감 경로를 지나므로 그 경로에 인자 하나를 더하는 작업입니다.

3.5build 객체

신규

장착한 장비·룬과 보유 증강을 담는 공통 객체입니다. 세이브 구조를 그대로 보내지 않고 분석에 필요한 값만 이 모양으로 옮겨 담기 때문에, 세이브 구조가 바뀌어도 이 모양은 유지됩니다.

key타입설명
weapons · 장착한 장비 (기본 4칸, 세트 효과로 최대 5칸)
slotint장착 칸 번호입니다. 0부터 셉니다.
templateIdint장비 종류입니다. 11001~11006 (부록 참고)
rankstring등급입니다. ENUM: C, B, A, S
runes · 장착한 룬 (0~2번 칸은 1성, 3번 칸은 2성 전용)
slotint장착 칸 번호입니다.
templateIdint룬 종류입니다. 21001 계절의 파편 / 21002 강력한 계절의 파편
seasonstring룬의 계절입니다. ENUM: SPRING, SUMMER, AUTUMN, WINTER
fusionStackint합성 진행도입니다. 1~3
augments · 보유한 증강
augmentIdint증강 종류입니다. 공격 타입 3종(10·11·12)도 여기 포함됩니다.
stacksint중첩 수입니다.
 
"build": {
  "weapons":  [ { "slot": 0, "templateId": 11001, "rank": "S" },
                { "slot": 1, "templateId": 11003, "rank": "A" } ],
  "runes":    [ { "slot": 0, "templateId": 21001, "season": "SPRING", "fusionStack": 2 },
                { "slot": 3, "templateId": 21002, "season": "WINTER", "fusionStack": 1 } ],
  "augments": [ { "augmentId": 12, "stacks": 3 }, { "augmentId": 15, "stacks": 1 } ]
}

가방에 든 아이템은 담지 않습니다. 장착하지 않은 아이템은 빌드에 영향을 주지 않기 때문입니다. 빈 칸은 배열에서 빠집니다. 가호(blessings)는 고른 목록이 클라이언트에 남지 않아 이번 버전에서는 뺐습니다.

스냅샷 규칙 신규

build는 보내는 시점의 구성이 아니라, 정해진 순간에 찍어 얼려 둔 사본입니다. 알고 싶은 것이 "이 스펙으로 이 스테이지를 어디까지 해냈는가"이기 때문입니다. 리워드로 받은 보상이 섞여 들어오면, 그 보상을 받기 전에 낸 성과를 보상 후의 스펙이 낸 것처럼 읽게 됩니다.

그래서 클라이언트는 아래 순간에 현재 장착·보유 상태로 스냅샷을 새로 만들고, 그 스냅샷을 해당 로그에 실어 보냅니다.

스냅샷을 찍는 순간실리는 로그보내는 시점
필드의 마지막 적을 처치한 순간 (예정된 적이 없는 필드는 포탈을 탄 순간)ROUND_CLEAR리워드·정비 후 Save 시점
보스의 HP가 0이 된 순간ROUND_CLEAR같음. 마지막 층의 보스는 그 자리에서 바로
OC가 0이 되어 죽은 순간PLAYER_DEATH그 자리에서 바로
(새로 찍지 않음)RUN_END그 판에서 마지막으로 찍힌 스냅샷을 그대로 씁니다
  • 스냅샷을 찍는 순간은 전부 "인게임에서 전투가 끝난 순간"입니다. 리워드 화면, 정비 화면, 합성, 장착 변경, 토큰 사용으로는 찍지 않고 갱신하지도 않습니다.
  • 한번 찍은 스냅샷은 다음 스냅샷을 찍을 때까지 그대로 둡니다. 그 사이에 인벤토리가 어떻게 바뀌든 이미 찍힌 값은 바뀌지 않아야 합니다.
  • 필드에 도착한 뒤 첫 입력 전까지 하는 정비는 스냅샷에 반영됩니다. 그 정비를 마친 상태로 전투를 치렀기 때문입니다.
  • 이어하기로 같은 스테이지를 다시 치르면 그때 다시 찍습니다. 남는 값은 마지막 것입니다.

이 규칙 덕분에 "리워드로 무엇을 골랐는가"도 복원됩니다. 어떤 스테이지의 ROUND_CLEAR 스냅샷과 다음 스테이지의 ROUND_CLEAR 스냅샷을 비교하면, 그 사이의 리워드·정비에서 바뀐 것이 그 차이로 남습니다.
