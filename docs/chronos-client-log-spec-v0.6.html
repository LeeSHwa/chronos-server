클라이언트 작업 목록

v0.5 → v0.6에서 클라이언트가 바꿔야 하는 것만 모았습니다. 10/25 실제 로그를 v0.5와 대조한 결과, 이벤트 순서와 구성은 명세대로 들어오고 있어 바뀌는 곳은 아래 몇 군데뿐입니다.

필수

  1. PLAYER_DEATH의 hazardId를 없애고 killerId 하나로 합칩니다. 타입은 string으로 고정합니다. 적이면 "2001", 장판이면 "RESIDUAL_BEAM"입니다. 3.4
  2. PLAYER_DEATH.deathCause ENUM을 MONSTER / HAZARD / DRAIN으로 확정합니다. 앞의 둘은 지금 보내는 값 그대로입니다. 3.4
  3. ROUND_ENTER에 currency(그 시점의 재화 잔량) 추가. 3.2
  4. ROUND_CLEAR에 clearCurrency(클리어한 순간의 재화 잔량, 상점에서 쓰기 전) 추가. 3.3

확인 부탁

  1. 재화 이름 — 이 명세는 평타 재화를 basic, 시간정지 재화를 timeStop으로 적었습니다. 클라이언트 쪽 이름이 따로 있으면 그쪽에 맞춥니다. 1.9
  2. SPECIAL_SHOT의 augmentId — v0.5 명세에는 12로 적었는데, 최근 SPECIAL_SHOT 판의 build에는 12 없이 8이 들어옵니다. CONVERSION 판은 10이 정상으로 들어옵니다. 3.5 · 제안 2
  3. 1-1 진입 로그 시점 — v0.5에서 "첫 진입 리워드를 고른 뒤"로 옮기기로 했는데, 지금은 RUN_START · FLOOR_ENTER · ROUND_ENTER가 1~3ms 간격으로 함께 나갑니다. 4.2
  4. 증강 강화 갈래 — 증강을 평타/시간정지 갈래로 따로 강화할 수 있게 됐다면, build.augments의 stacks 하나로는 갈래가 구분되지 않습니다. 갈래별 단계가 따로 있는지 알려주세요. 3.5 · 제안 1
  5. 아직 실제 로그로 확인 못 한 것 — RUN_END(QUIT)과 CLIENT_ERROR. 테스트로 한 번씩 발생시켜 주세요. 2.4 · 2.5

다음 단계 (이번 작업 범위 밖, 합의만 해두는 것)

  1. 상점 체결 로그 — 상점을 장바구니형(담고 확인)으로 바꾼다면 확인 시점에 한 건을 남기는 안입니다. 제안 1에 정리했습니다. v0.5의 REWARD_PICK은 라운드 리워드가 상점으로 바뀌면서 이 안으로 대체합니다.
  2. 클라이언트 버전과 데이터 정의 — 빌드마다 clientVersion을 올리고, 그 버전의 증강·장비·적·맵 정의를 파일로 뽑아 받는 안입니다. 제안 2에 정리했습니다.
  3. RELIC_WAGER — 보스에서 OC가 0이 됐을 때 열리는 성물 베팅의 결과. 판당 1회뿐이지만 판 성패를 직접 가릅니다.
  4. 가호(blessings) — 고른 목록이 클라이언트에 남지 않고 합산 스탯만 있어, build에서는 계속 뺍니다.

로그 구조와 이벤트 타입

모든 로그가 공통으로 갖는 필드와 이벤트 타입 전체 목록입니다.

1.1전송 흐름

Unity 클라이언트LogManager
→ JSON 배열 →
Chronos 서버POST /api/v1/logs
→
PostgreSQLgame_events

로그 한 건은 공통 필드와 payload로 나뉩니다. 공통 필드는 테이블의 일반 컬럼이 되어 필터와 집계에 바로 쓰이고, payload는 이벤트마다 다른 상세 정보로 JSONB 컬럼 하나에 그대로 저장됩니다.

클라이언트는 로그를 큐에 쌓아 15초마다 최대 20건씩 묶어 보냅니다. 전송에 실패하면 순서를 지킨 채 다시 보내고, 게임을 끄면 남은 로그를 디스크에 저장했다가 다음 실행 때 이어서 보냅니다.

// 요청 본문 예시
[
  {
    "userId": -6601403713907716966,
    "eventType": "ROUND_CLEAR",
    "timestamp": "2026-10-25T13:24:05.1234567Z",
    "difficulty": "Standard",
    "runId": -8553994346255530530,
    "floor": 1,
    "round": "2",
    "payload": {
      "clearElapsedMs": 84210,
      "clearOverclockDeciseconds": 731,
      "clearCurrency": { "basic": 14, "timeStop": 6 },
      "build": { "weapons": [ ... ], "runes": [ ... ], "augments": [ ... ] }
    }
  }
]

1.2공통 필드

클라이언트의 ClientLogEnvelope가 모든 이벤트에 붙이는 8개 필드입니다. 현행 구성을 그대로 유지합니다.

필드타입DB 컬럼발행 시점설명
userIdlonguser_id모든 로그게임이 설치된 기기마다 하나씩 발급되는 번호입니다. 사람이 아니라 기기를 구분하므로, 재설치하면 새 유저로 잡힙니다.

1.3스테이지를 가리키는 값

스테이지는 필드와 보스 두 종류입니다. 클리어 뒤에 들르는 상점·정비 필드(F1_Rest, F2_Rest)는 스테이지 사이를 잇는 공간이라 스테이지로 세지 않고, ROUND_ENTER · FLOOR_ENTER를 보내지 않습니다. 1층 필드 4개는 판마다 순서가 섞이므로, "몇 번째로 들어간 스테이지인가"와 "어떤 맵인가"를 따로 기록합니다.

값위치예시용도
floor · round공통 필드1 · "1" … 1 · "4", 1 · "B"플레이어가 지나간 순서입니다. 문자열로 정렬해도 "1" < "2" < … < "B" 순서가 됩니다.
mapIdROUND_ENTER payload"F1_3", "F1_B"실제로 들어간 맵의 씬 이름입니다. 몇 번째 자리에서 나왔는지와 상관없이 맵 단위로 묶을 때 씁니다.

클리어나 사망 같은 다른 스테이지 이벤트는 맵을 싣지 않고, 같은 runId·floor·round의 ROUND_ENTER에서 가져옵니다. 이 둘을 나눠 두면 "F1_3이 어려운 것"과 "3번째 자리가 어려운 것"을 분리해서 볼 수 있습니다.

1.7payload 작성 규칙

  • key는 camelCase로 씁니다.
  • 시간과 OC는 클라이언트가 재는 단위를 그대로 쓰고, key 이름 끝에 단위를 붙입니다. 예: elapsedMs(밀리초), overclockDeciseconds(0.1초)
  • payload 안의 ENUM 값은 UPPER_SNAKE_CASE로 씁니다. 예: DEATH, SPRING
  • 값이 없으면 key를 생략하고 null을 넣지 않습니다.
  • 같은 의미에는 모든 이벤트에서 같은 key를 씁니다.
  • 장비·룬·증강 구성은 어느 이벤트에서든 같은 모양의 build 객체로 담습니다. 재화도 마찬가지로 같은 모양의 객체로 담습니다(1.9).
  • eventType마다 payload의 key 구성은 고정입니다. 이 명세의 표에 있는 key만 보내고, 조건에 따라 빠지는 key는 그 조건을 표에 함께 적습니다. 한 key에 타입을 섞지 않습니다(숫자와 문자열 등). 신규

1.8시간과 OC 기준

  • 플레이 시간 elapsedMs: 이번 판에서 실제로 플레이한 누적 시간입니다. 이어하기를 해도 이어서 셉니다.
  • OC 잔량 overclockDeciseconds: 게임 안의 제한 시간이자 체력입니다. 0.1초 단위입니다.
  • 스테이지 소요 시간은 ROUND_CLEAR의 clearElapsedMs에서 같은 스테이지 ROUND_ENTER의 elapsedMs를 뺀 값입니다. ROUND_CLEAR는 상점과 정비가 끝난 뒤에 나가지만 클리어한 순간의 값을 따로 담으므로, 상점과 정비 시간은 스테이지 소요 시간에 섞이지 않습니다.
  • OC 지급 규칙은 로그에 적지 않습니다. 라운드 지급분이 얼마인지, 언제 들어오는지는 클라이언트의 규칙이고, 로그는 그 결과인 그 순간의 잔량만 적습니다. 규칙이 바뀌어도 로그 형식은 바뀌지 않습니다.
  • 그래서 기준만 분명히 해 둡니다 — ROUND_ENTER의 OC는 그 라운드 지급분이 들어오기 전, ROUND_CLEAR의 OC는 들어온 뒤입니다.

1.9재화 기준 신규

적을 어떻게 처치했느냐에 따라 두 가지 재화가 쌓이고, 상점·정비 필드에서 이 재화로 증강을 그 재화 성격에 맞는 갈래로 강화합니다. 로그에는 OC와 마찬가지로 그 순간의 잔량만 적습니다. 얼마를 얻었는지, 얼마를 썼는지는 잔량의 차이로 계산합니다.

key타입설명
basicint평타 재화 잔량입니다. 평타로 처치하면 쌓이고, 평타 갈래 강화에 씁니다.
timeStopint시간정지 재화 잔량입니다. 시간정지 스킬로 처치하면 쌓이고, 시간정지 갈래 강화에 씁니다.
 
{ "basic": 14, "timeStop": 6 }
  • 재화가 0이어도 key를 생략하지 않고 0을 넣습니다. 잔량은 "없음"이 아니라 "0개"이기 때문입니다.
  • 재화 종류가 늘어나면 이 객체에 key를 추가합니다. 이벤트마다 재화 key를 따로 늘어놓지 않습니다.
알고 싶은 것계산
한 스테이지에서 얻은 재화그 스테이지 ROUND_CLEAR의 clearCurrency − 같은 스테이지 ROUND_ENTER의 currency
상점에서 쓴 재화그 스테이지 ROUND_CLEAR의 clearCurrency − 다음 스테이지 ROUND_ENTER의 currency
플레이 스타일 (평타 위주 / 시간정지 위주)스테이지에서 얻은 basic과 timeStop의 비율

ROUND_CLEAR의 재화는 클리어한 순간 값이고, 다음 ROUND_ENTER의 재화는 상점을 나온 뒤 값입니다. 그래서 상점에서 쓴 양이 그 사이의 차이로 정확히 남습니다. 클리어 뒤 상점에 들어가기 전에 재화가 더 들어오는 규칙이 있다면, 그만큼 "쓴 재화"가 작게 계산되므로 알려주세요.

3장

스테이지 이벤트와 build

스테이지에 들어가고, 클리어하고, 죽는 순간의 이벤트입니다. 마지막 절에 장비·룬·증강을 담는 build 객체의 구조를 정리했습니다.

3.1FLOOR_ENTER

현행
발행 시점
새 층에 들어갈 때. 판 시작의 1층 진입도 포함하며, 바로 뒤에 같은 스테이지의 ROUND_ENTER가 나갑니다.
공통 필드
runId, floor 있음. round는 그 층에서 처음 들어가는 스테이지의 값입니다.
key타입설명
fieldCountint이 층의 필드 수입니다. 지금 1층은 4, 2층은 3입니다.
hasBossbool이 층에 보스 스테이지가 있는지입니다. 지금은 두 층 모두 보스가 있습니다.

3.2ROUND_ENTER

변경currency 추가
발행 시점
포탈을 타고 상점·정비 필드를 나와, 다음 스테이지를 불러오기 직전. 세이브와 같은 시점입니다. 1-1은 첫 진입 리워드를 고른 직후입니다. 상점·정비 필드에 들어갈 때는 보내지 않습니다.
공통 필드
runId, floor, round 있음. 들어가는 스테이지 기준입니다.
key타입설명
mapIdstring들어가는 맵의 씬 이름입니다. 예: "F1_3", "F1_B"
elapsedMslong이 시점의 누적 플레이 시간입니다. 스테이지 소요 시간의 시작점입니다.
overclockDecisecondsint이 시점의 OC 잔량입니다. 이번 스테이지에서 받을 라운드 지급분은 아직 들어오기 전입니다.
currencyobject이 시점의 재화 잔량입니다. 상점에서 쓰고 남은 값이며, 이 스테이지에서 얻는 재화의 시작점입니다. 모양은 1.9. 신규
 
{ "mapId": "F1_3", "elapsedMs": 84210, "overclockDeciseconds": 731, "currency": { "basic": 2, "timeStop": 0 } }

build는 싣지 않습니다. 필드에 도착한 뒤 첫 입력 전까지 장착을 바꿀 수 있어서, 이 시점의 구성이 실제로 그 스테이지를 플레이한 구성과 다를 수 있기 때문입니다. 구성은 ROUND_CLEAR에 담습니다. 스테이지별 진입 수를 세는 기준이 되는 이벤트입니다.

3.3ROUND_CLEAR

변경clearCurrency 추가
발행 시점
  • 스테이지를 클리어하고, 포탈을 타서 상점·정비 필드를 나와 Save되는 순간. 다음 스테이지의 ROUND_ENTER 바로 앞에 나갑니다.
  • 마지막 층의 보스는 다음 스테이지가 없으므로 쓰러뜨린 순간에 나가고, 바로 뒤에 RUN_END(WIN)가 이어집니다.
공통 필드
runId, floor, round 있음. 클리어한 스테이지 기준입니다.
key타입설명
clearElapsedMslong클리어한 순간의 누적 플레이 시간입니다. 필드는 예정된 적을 모두 처치한 순간(예정된 적이 없으면 포탈을 탄 순간), 보스는 HP가 0이 된 순간입니다. ROUND_ENTER의 elapsedMs와의 차이가 그 스테이지의 소요 시간입니다.
clearOverclockDecisecondsint클리어한 순간의 OC 잔량입니다. 그 라운드 지급분은 이미 들어온 뒤입니다.
clearCurrencyobject클리어한 순간의 재화 잔량입니다. 이 스테이지에서 얻은 재화는 들어온 뒤이고, 상점에서 쓰기 전입니다. 모양은 1.9. 신규
buildobject클리어한 순간의 장비·룬·증강입니다. 로그는 Save 시점에 나가지만 이 값은 그 전에 찍어 둔 스냅샷이며, 상점과 정비는 반영되지 않습니다.
 
{ "clearElapsedMs": 84210, "clearOverclockDeciseconds": 731, "clearCurrency": { "basic": 14, "timeStop": 6 }, "build": { ... } }

이 이벤트에 실리는 네 값은 모두 클리어한 순간에 찍어 둔 것입니다. 로그가 나가는 시점(Save)과 값이 가리키는 시점(클리어)이 다른 유일한 이벤트입니다. 스냅샷 규칙은 3.5를 보세요. 재화를 클리어 순간 값으로 두는 이유는, 그래야 다음 ROUND_ENTER의 currency와의 차이가 곧 상점에서 쓴 양이 되기 때문입니다(1.9). 보스 처치도 보스 스테이지의 ROUND_CLEAR로 기록합니다.

3.4PLAYER_DEATH

변경killerId 통합 · deathCause 확정
발행 시점
OC가 0이 되어 플레이어가 죽은 순간. 바로 뒤에 RUN_END(DEATH)가 나갑니다.
공통 필드
runId, floor, round 있음. 죽은 스테이지입니다.
key타입언제설명
deathCausestring항상OC를 마지막으로 깎은 원인입니다. ENUM: MONSTER(적에게 맞음, 보스 포함), HAZARD(장판·투사체 잔여물 등 맵 위의 위험 요소), DRAIN(가해자 없이 시간이 흘러 바닥남) 변경
killerIdstringMONSTER · HAZARD일 때마지막으로 OC를 깎은 대상의 id입니다. 적이면 적 id("2001"), 장판이면 장판 id("RESIDUAL_BEAM")입니다. DRAIN이면 가해자가 없으므로 key를 생략합니다. 변경
elapsedMslong항상죽은 순간의 누적 플레이 시간입니다.
buildobject항상사망 시점의 장비·룬·증강입니다.
 
// 적에게 죽음
{ "deathCause": "MONSTER",
  "killerId": "2001",
  "elapsedMs": 3711,
  "build": { ... } }
// 장판에 죽음
{ "deathCause": "HAZARD",
  "killerId": "RESIDUAL_BEAM",
  "elapsedMs": 18679,
  "build": { ... } }
  • hazardId는 삭제합니다. 적이든 장판이든 "무엇에 죽었나"라는 같은 의미이므로 같은 key에 담습니다(1.7). 무엇의 id인지는 deathCause가 알려줍니다.
  • killerId는 항상 문자열입니다. 적 id는 숫자, 장판 id는 이름이라, 한 key에 두 타입이 섞이지 않도록 적 id도 "2001"처럼 문자열로 보냅니다.
  • v0.5의 COMBAT · REFLECT는 MONSTER로 합칩니다. 보스 돌진 반사도 가해자가 보스이므로 MONSTER + 보스 id입니다.
  • overclockDeciseconds는 넣지 않습니다. 죽는 순간에는 항상 0입니다.

죽은 판은 ROUND_CLEAR가 나가지 않으므로, 여기에 build가 없으면 그 판의 구성을 알 수 없습니다. 이 구성이면 GROUP BY deathCause, killerId 한 번으로 적과 장판을 합친 "가장 많이 죽인 것" 순위가 나옵니다.

3.5build 객체

현행

장착한 장비·룬과 보유 증강을 담는 공통 객체입니다. 세이브 구조를 그대로 보내지 않고 분석에 필요한 값만 이 모양으로 옮겨 담기 때문에, 세이브 구조가 바뀌어도 이 모양은 유지됩니다.

key타입설명

runes · 장착한 룬 (0~2번 칸은 1성, 3번 칸은 2성 전용)

"build": {
  "weapons":  [ { "slot": 0, "templateId": 11001, "rank": "S" },

  "runes":    [ { "slot": 0, "templateId": 21001, "season": "SPRING", "fusionStack": 2 },

스냅샷 규칙

build는 보내는 시점의 구성이 아니라, 정해진 순간에 찍어 얼려 둔 사본입니다. 알고 싶은 것이 "이 스펙으로 이 스테이지를 어디까지 해냈는가"이기 때문입니다. 상점에서 강화한 결과가 섞여 들어오면, 강화하기 전에 낸 성과를 강화 후의 스펙이 낸 것처럼 읽게 됩니다.

그래서 클라이언트는 아래 순간에 현재 장착·보유 상태로 스냅샷을 새로 만들고, 그 스냅샷을 해당 로그에 실어 보냅니다.

스냅샷을 찍는 순간실리는 로그보내는 시점
필드의 마지막 적을 처치한 순간 (예정된 적이 없는 필드는 포탈을 탄 순간)ROUND_CLEAR상점·정비 후 Save 시점
보스의 HP가 0이 된 순간ROUND_CLEAR같음. 마지막 층의 보스는 그 자리에서 바로
OC가 0이 되어 죽은 순간PLAYER_DEATH그 자리에서 바로
(새로 찍지 않음)RUN_END그 판에서 마지막으로 찍힌 스냅샷을 그대로 씁니다
  • 스냅샷을 찍는 순간은 전부 "인게임에서 전투가 끝난 순간"입니다. 상점, 정비 화면, 합성, 장착 변경, 토큰 사용으로는 찍지 않고 갱신하지도 않습니다.
  • 한번 찍은 스냅샷은 다음 스냅샷을 찍을 때까지 그대로 둡니다. 그 사이에 인벤토리가 어떻게 바뀌든 이미 찍힌 값은 바뀌지 않아야 합니다.
  • 필드에 도착한 뒤 첫 입력 전까지 하는 정비는 스냅샷에 반영됩니다. 그 정비를 마친 상태로 전투를 치렀기 때문입니다.
  • 이어하기로 같은 스테이지를 다시 치르면 그때 다시 찍습니다. 남는 값은 마지막 것입니다.

이 규칙 덕분에 "상점에서 무엇을 강화했는가"도 복원됩니다. 어떤 스테이지의 ROUND_CLEAR 스냅샷과 다음 스테이지의 ROUND_CLEAR 스냅샷을 비교하면, 그 사이의 상점·정비에서 바뀐 것이 그 차이로 남습니다. 재화(clearCurrency)도 같은 순간에 함께 찍습니다.

  • ROUND_CLEAR는 Save 시점에 나가므로, 클리어하고 상점을 나오기 전에 껐다면 그 스테이지의 ROUND_CLEAR는 아직 나가지 않은 상태입니다. 이어하기 후 다시 클리어할 때 한 번만 나갑니다.
  • 보스에서 끈 판은 그 층의 마지막 필드로 돌아오므로, 마지막 필드의 ROUND_CLEAR와 보스의 ROUND_ENTER가 한 번 더 나갑니다.
제안 1

상점 체결 로그

이번 버전에서 구현할 내용이 아닙니다. 상점을 "담고 확인하는" 장바구니형으로 바꾼다면 이렇게 기록하자는 제안입니다.

P1.1왜 필요한가

지금도 ROUND_CLEAR의 build를 앞뒤로 비교하면 상점에서 무엇이 바뀌었는지는 알 수 있습니다. 하지만 "사람들이 가장 많이 강화하는 증강은 무엇인가"를 보려면 판마다 스냅샷 차이를 계산해 다시 모아야 하고, 갈래(평타/시간정지)까지 나누면 계산이 더 복잡해집니다. 산 것을 그 자리에서 한 번 적어 두면 이 질문이 쿼리 한 줄이 됩니다.

P1.2건별이 아니라 체결 한 번에 1건

방식장점단점
담을 때마다 1건–담았다 뺀 것까지 섞여 실제로 산 것과 구분해야 함. 방문 단위로 다시 묶어야 함
확인을 누를 때 1건확정된 구매만 남음. 이벤트 수 = 상점 방문 수. 아무것도 안 산 방문도 purchases: []로 남음담았다 뺀 망설임은 남지 않음 (필요하면 그때 추가)

P1.3SHOP_CHECKOUT

제안
발행 시점
상점·정비 필드에서 확인을 눌러 구매가 체결되는 순간. 아무것도 사지 않고 나가도 한 번 보냅니다.
공통 필드
runId, floor, round 있음. 직전에 클리어한 스테이지 기준입니다.
key타입설명
currencyBeforeobject체결 전 재화 잔량입니다(1.9). 돈이 없어서 못 산 것인지, 있는데 안 산 것인지를 가릅니다.
purchasesarray이번에 체결된 구매 목록입니다. 아무것도 안 샀으면 빈 배열입니다.
currencyAfterobject체결 후 재화 잔량입니다.
purchases의 한 칸
augmentIdint강화한 증강입니다.
branchstring강화한 갈래입니다. ENUM: BASIC(평타), TIME_STOP(시간정지)
costint쓴 재화입니다. 어떤 재화인지는 branch를 따릅니다.
levelAfterint강화 후 그 갈래의 단계입니다.
 
{
  "currencyBefore": { "basic": 12, "timeStop": 5 },
  "purchases": [
    { "augmentId": 8,  "branch": "BASIC",     "cost": 6, "levelAfter": 2 },
    { "augmentId": 14, "branch": "TIME_STOP", "cost": 5, "levelAfter": 1 }
  ],
  "currencyAfter": { "basic": 6, "timeStop": 0 }
}
-- 가장 많이 강화된 증강과 갈래
select p ->> 'augmentId' as augment, p ->> 'branch' as branch, count(*)
from game_events, jsonb_array_elements(payload -> 'purchases') p
where event_type = 'SHOP_CHECKOUT'
group by 1, 2
order by 3 desc;

상점에 증강 전체가 아니라 일부만 진열된다면, 진열된 목록(offered)도 함께 남겨야 "진열됐을 때 얼마나 골랐나"(선택률)를 계산할 수 있습니다. 보유한 증강이 모두 진열된다면 직전 ROUND_CLEAR의 build로 알 수 있어 필요 없습니다.

P1.4같이 바꿀 것 — build의 증강 갈래

증강을 갈래별로 따로 강화한다면, build의 증강 한 칸에도 갈래별 단계를 담아야 스냅샷만으로 구성을 읽을 수 있습니다. 클라이언트 데이터 구조가 이렇다면 stacks를 아래처럼 나눕니다.

"augments": [ { "augmentId": 8, "basicLevel": 2, "timeStopLevel": 0 },
              { "augmentId": 14, "basicLevel": 0, "timeStopLevel": 1 } ]

지금 build의 stacks가 갈래 강화와 어떤 관계인지 먼저 알려주세요(0장 확인 부탁 4).

제안 2

클라이언트 버전과 데이터 정의

이번 버전에서 구현할 내용이 아닙니다. 가능한지 확인하고 방식을 합의하고 싶은 제안입니다.

P2.1왜 필요한가

로그에는 숫자 id만 들어오고, 그 id가 무엇인지(이름, 수치)는 클라이언트의 데이터 정의에 있습니다. 지금은 서버가 이 대응표를 손으로 옮겨 적고 있어서, 표에 없는 증강은 어드민 화면에 증강 #8처럼만 나오고, 버전이 바뀌면 표가 어긋납니다. 실제로 v0.5 명세에 SPECIAL_SHOT의 augmentId를 12로 적었는데, 최근 로그에는 8이 들어옵니다.

그래서 두 가지를 같이 하자는 제안입니다.

할 일얻는 것
빌드마다 clientVersion을 올린다어떤 로그가 어느 빌드에서 나왔는지 구분됩니다. 밸런스 패치 전후를 나눠 볼 수 있습니다.
그 버전의 데이터 정의를 파일로 뽑는다서버가 버전별로 보관해, 로그의 id에 그 판이 플레이된 버전 기준의 이름과 수치를 붙입니다. "1.0.3의 증강 8"과 "1.0.4의 증강 8"을 따로 읽을 수 있습니다.

P2.2clientVersion을 빌드마다 올리기

지금 모든 로그의 clientVersion이 "1.0"으로 고정되어 있습니다. 빌드할 때마다 바뀌는 값이면 형식은 자유입니다. 예: 1.0.3, 1.0+빌드번호

  • 이 값을 Application.version(Player Settings의 Version)에서 읽고 있다면, 빌드할 때 그 값만 올리면 됩니다.
  • 로그에서 실리는 곳은 지금과 같습니다: ACCOUNT_LOGIN, RUN_START, CLIENT_ERROR. 판 안의 다른 로그는 runId로 RUN_START와 이으면 버전을 알 수 있으므로 공통 필드로 올리지 않습니다.
  • 같은 버전 문자열로 내용이 다른 빌드를 내지 않습니다. 버전이 같으면 데이터 정의도 같다고 보고 P2.3의 파일을 찾기 때문입니다.

P2.3데이터 정의를 버전별 파일로 뽑기

빌드할 때 에디터 메뉴나 빌드 스크립트로 catalog-<clientVersion>.json 한 파일을 뽑아 전달하는 방식을 제안합니다. 처음에는 파일을 직접 전달하는 것으로 충분하고, 게임이 서버에 자동으로 올리는 방식은 필요해지면 그때 정합니다.

대상로그에서 쓰는 곳담을 것
증강build.augments[].augmentIdid, 이름, 평타/시간정지 갈래별 효과(가능하면)
공격 타입RUN_START.attackType로그 값과 대응하는 augmentId
장비 · 룬build.weapons / runes[].templateIdid, 이름, 분류(장비·룬·소모품)
적PLAYER_DEATH.killerIdid, 이름, 나오는 층
장판PLAYER_DEATH.killerIdid, 이름
맵ROUND_ENTER.mapId씬 이름, 층, 종류(필드·보스·상점정비)
 
// catalog-1.0.3.json
{
  "clientVersion": "1.0.3",
  "augments":    [ { "id": 8, "name": "..." } ],
  "attackTypes": [ { "value": "SPECIAL_SHOT", "augmentId": 8 } ],
  "items":       [ { "id": 11001, "name": "학살", "kind": "WEAPON" } ],
  "enemies":     [ { "id": "2001", "name": "F1_A1", "floor": 1 } ],
  "hazards":     [ { "id": "RESIDUAL_BEAM", "name": "..." } ],
  "maps":        [ { "id": "F1_1", "floor": 1, "kind": "FIELD" },
                   { "id": "F1_Rest", "floor": 1, "kind": "SHOP" } ]
}

이 파일이 들어오면 v0.5까지 명세 부록에 손으로 적던 id 표는 더 이상 필요 없습니다. 이름이 바뀌어도 로그는 그대로 두고, 버전별 파일만 새로 받습니다.

확인 부탁

  1. 위 데이터가 지금 클라이언트에 어떤 형태로 있나요? (ScriptableObject / CSV / JSON / 코드 상수 등) 형태에 따라 뽑는 방법이 달라집니다.
  2. clientVersion은 지금 어디서 읽고 있나요? 빌드마다 올리는 흐름을 만들 수 있을까요?
  3. 이름만이 아니라 수치(증강 효과, 강화 비용 등)도 같이 뽑을 수 있나요? 수치가 있으면 밸런스 패치 전후를 비교할 수 있습니다.
  4. 19001~19003(예견된 종말·이상현상·태풍의 눈)은 장비인지 소모품인지 — 파일의 kind로 받으면 됩니다.
